## Versions and PHP

Grav 2.0 is the current release and needs PHP 8.3 or newer. fortrabbit offers PHP 8.3, 8.4 and 8.5, so any [PHP version](/1.platform/07.settings/06.php.md) on the platform runs it. Grav 1.7 still receives updates and runs up to PHP 8.3. Both majors can be selected as software version when creating an app.

## Choose a deployment workflow

Grav writes to its own files while it runs. Pages, user accounts, uploads and generated caches all change on the environment, so anything the CMS writes has to stay out of the deploy package:

- rsync — recommended, works for the whole site
- git for the code plus rsync for the content — for projects under version control
- [SFTP](/1.platform/05.code-access/04.sftp.md) — a one-off upload
- git only — when nothing is edited through the admin panel on the environment

## Install with rsync

1. Download the "Grav Core + Admin plugin" package from the [Grav website](https://getgrav.org/downloads) and unpack it locally.
2. Sync the **contents** of the local `grav-admin` folder (not the folder itself) to the `htdocs` folder of the environment:

```shell
# from inside the unpacked grav-admin folder
$ rsync -av ./ {{app-env-id}}@ssh.{{region}}.frbit.app:htdocs/
```

3. Create the first admin account over [SSH](/1.platform/05.code-access/03.ssh.md):

```shell
$ php bin/plugin login new-user -u USERNAME -e EMAIL -P b
```

The `-P b` flag grants access to both the site and the admin panel. Without a command line account, the guided web installation asks for the same details on first visit.

See the [rsync article](/3.dev/20.how-to/rsync.md) for syncing changes up and down later on.

## Deploy code with git and content with rsync

This is the more advanced route: the code lives in a git repo, the content stays on the environment. See the [git deployment intro](/1.platform/06.deployment/01.intro.md) for connecting a repo.

Keep everything Grav writes out of the repo. Add these rules to `.gitignore` in the project root:

```shell
# .gitignore

# Composer, installed by the build command
/vendor

# Written by Grav at runtime
/cache
/logs
/tmp
/backup
/images
/assets

# Owned by the environment, synced with rsync
/user/pages
/user/accounts
/user/data
/user/config
```

The [software template](/1.platform/03.concepts/05.software-templates.md) preconfigures the matching deployment settings when Grav is chosen as software: the [replace strategy](/1.platform/06.deployment/08.strategy.md) with the same paths as [exclude patterns](/1.platform/06.deployment/10.exclude-patterns.md), a `composer install` [build command](/1.platform/06.deployment/03.build-commands.md), and a [post-deploy command](/1.platform/06.deployment/04.post-deploy-commands.md) that recreates the empty runtime folders:

```shell
$ mkdir -p logs tmp backup images assets user/pages user/accounts user/data user/config
```

Grav refuses to boot when one of those folders is missing, and none of them are in the repo.

Content moves with rsync, in both directions:

```shell
# SYNC UP: local pages to the environment
$ rsync -av ./user/pages/ {{app-env-id}}@ssh.{{region}}.frbit.app:htdocs/user/pages/

# SYNC DOWN: pages edited in the admin panel back to the local project
$ rsync -av {{app-env-id}}@ssh.{{region}}.frbit.app:htdocs/user/pages/ ./user/pages/
```

Seed `user/config` the same way on first setup. After that it belongs to the environment.

::CallOut
Plugins and themes count as code here. Install them locally, commit, then push — a plugin installed through the admin panel on the environment is gone after the next deployment. Configuration goes the other way: the admin panel writes to `user/config`, and so do plugins that generate their own secrets, so that folder is excluded from deployment and changes there have to be made on the environment.
::

## Configuration through environment variables

Grav 2 reads a `.env` file at the project root and accepts configuration overrides from real environment variables, which is the better fit for [fortrabbit environment variables](/1.platform/07.settings/01.env-vars.md). Set `GRAV_CONFIG` to switch the feature on, then map any config path to a variable name by replacing the dots with double underscores:

```shell
GRAV_CONFIG=true
GRAV_CONFIG__system__cache__enabled=true
GRAV_CONFIG__plugins__email__mailer__smtp__password=secret
```

Server-set variables win over anything in a `.env` file, so secrets belong in the dashboard rather than in the repo. The shipped `.env.example` documents the remaining options, including the `GRAV_CONFIG_ALIAS__` prefix for plugin slugs containing a hyphen.

## Environment configuration by domain

Grav also configures [different settings based on the domain](https://learn.getgrav.org/advanced/environment-config) it is served from. For a site under development locally, debugging is usually wanted there and unwanted on fortrabbit. Create a `system.yaml` for the custom domain — for `www.my-grav.tld` that is `user/www.my-grav.tld/config/system.yaml`:

```yml
debugger:
  enabled: false
```

The stricter approach sets `user/config/system.yaml` as restrictive as possible and keeps a localhost override in `user/localhost/config/system.yaml`:

```yml
debugger:
  enabled: true
```

## Upgrade from Grav 1.x to 2.x

`bin/gpm selfupgrade` does not cross the major boundary. A 1.7 installation keeps receiving 1.7 releases and reports that 2.0 is available without installing it. Follow the [Grav 2 migration guide](https://getgrav.org/migrate-to-2), and update all plugins and themes to their latest compatible versions before the core.

Take a [backup](/1.platform/25.backups/index.md) first, and raise the [PHP version](/1.platform/07.settings/06.php.md) to 8.3 or newer if the environment still runs an older one.
