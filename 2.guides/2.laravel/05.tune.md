## Get ready

You have already started your Laravel on fortrabbit journey with the [setup](/2.guides/2.laravel/02.setup.md) and with [deployment](/2.guides/2.laravel/03.deployment.md). This is the final article to address most common configuration options to successfully run Laravel based applications on fortrabbit.

## Emoji support

<!-- TODO: Review by infra! -->

Laravel uses the `utf8mb4` character set by default, which includes support for storing "emojis 🔥" in the database. You need to manually configure the default string length generated by migrations so that [MySQL](/1.platform/09.components/02.mysql.md) can create indexes for them in your `AppServiceProvider`:

```php
use Illuminate\Support\Facades\Schema;

/**
 * Bootstrap any application services.
 *
 * @return void
 */
public function boot()
{
  Schema::defaultStringLength(191);
}
```

## Manually running artisan migrate

While it's recommended to [run database migrations automatically](/2.guides/2.laravel/03.deployment.md#migration-build-step) each time you deploy, you can also do that manually. Log in by [SSH](/1.platform/05.code-access/03.ssh.md) and execute `artisan`:

```shell
# login and execute
$ ssh {{app-env-id}}@ssh.{{region}}.frbit.app
$ php artisan migrate --force
```

**Note**: If `APP_ENV` is set to `production` - which is the default - the `--force` flag for migrate commands will override the confirmation prompt. You can also add this command to your `composer.json` to have it run automatically every time you push changes.

```json [composer.json]
"scripts": {
  "post-install-cmd": [
    "php artisan migrate --no-interaction --force",
  ],
}
```

With that in place, any time you deploy your code, database changes will be applied immediately. If no database changes are required, nothing happens, so it is safe to run all the time. Just make sure to test your upgrades and migrations locally first.

## Logging

Logs for Laravel are stored in `storage/logs` per default. Our [software preset](/1.platform/03.concepts/05.software-templates.md) for Laravel pre-configures log output to `stderr` and `stdout`, making logs available in the dashboard - see the [logging article](/1.platform/07.settings/25.logs.md).

If for some reason you cannot access the logs in the dashboard, see if you can access these via [SSH](/1.platform/05.code-access/03.ssh.md) or [SFTP](/1.platform/05.code-access/04.sftp.md).

See [Laravel logging help](https://laravel.com/docs/logging) for more.

## User sessions

Laravel supports multiple session storage drivers; the most common are `file` (default) and `database`. Configure your chosen driver by setting the `SESSION_DRIVER` environment variable in the dashboard. Since fortrabbit environments have persistent storage, you can use the default `file` driver for sessions.

To use the `database` driver, follow these steps:

```shell
# Create a migration for the session table  - locally
$ php artisan session:table

# Apply the migration - locally
$ php artisan migrate

# Add, commit and push the migration file
$ git add .
$ git commit -m "session migration"
$ git push

# Run the migration on the App via SSH remote execution
$ ssh {{app-env-id}}@ssh.{{region}}.frbit.app php artisan migrate --force
```

## Queueing

Laravel supports multiple queue drivers. The `database` driver works with fortrabbit out of the box and simply uses your database connection as a queue:

```shell
# Create a migration for the jobs table locally
php artisan queue:table

# Apply the migration locally
$ php artisan migrate

# Add, commit and push the migration file
$ git add .
$ git commit -m "queue migration"
$ git push

# Run the migration on the App via SSH remote execution
$ ssh {{app-env-id}}@ssh.{{region}}.frbit.app php artisan migrate --force
```

<!-- That's great for small use-cases and tinkering, but if your application handles very many queue messages you should consider using the [key-value store](/1.platform/09.components/08.key-value-store.md) (WIP). -->

Once you've decided the queue you want to use, just open `config/queue.php` and set `default` to either `redis`, `database`, `sqs` - or even better: set the `QUEUE_CONNECTION` environment variable accordingly in the dashboard.

To run `php artisan queue:work` in the background, spin up a new [worker job](/1.platform/09.components/07.jobs.md) and define the artisan command as a job.

Laravel offers two commands to process queues: `queue:work` and `queue:listen`. We recommend using `queue:work`, and _not_ using `queue:listen`. This is because the `queue:listen` command boots the Laravel framework for each iteration, whereas `queue:work` boots the framework once and runs as a daemon. Using `queue:work` offers high memory and performance gains in comparison with `queue:listen`.

## Scheduling

Laravel's scheduler lets you define recurring tasks in code instead of managing many separate crontab entries. Add a single [cron job](/1.platform/30.jobs/02.crons.md) that runs every minute and let Laravel decide what's actually due:

```shell
* * * * * php artisan schedule:run
```

See [job usage](/1.platform/30.jobs/01.usage.md) for adding the cron job in the dashboard.

Here are two things to keep in mind when adding crons to laravel:

- Avoid laravels `->runInBackground()`, it will not work at all with `schedule:run`. We have to keep the platform performant for everyone, so we kill any process still running after the job that started it exits - see ["do not detach"](/1.platform/30.jobs/05.tuning.md#do-not-detach). If you have to use `runInBackground()`, then it works better with a non stop job that calls `artisan schedule:work` instead, because that parent job stays running.
- Use `->withoutOverlapping()` on tasks that might run long. It stops Laravel from starting a new instance of a task while a previous run is still in progress, keeping `schedule:run` itself fast. Without it, slow tasks pile up invocation after invocation and can hit the platform's own limit on concurrent instances of the same cron job - see ["overlapping jobs"](/1.platform/30.jobs/05.tuning.md#overlapping-jobs).

## Using artisan down

`artisan down` generates the file `storage/framework/down`, which is then checked from your app's HTTP kernel with the `CheckForMaintenanceMode` middleware. You can run this command via [SSH](/1.platform/05.code-access/03.ssh.md) or during deployment.

## Using Laravel Envoy

Use Envoy to automate tasks on your fortrabbit environment. Here's an example `Envoy.blade.php` configuration:

```php
@servers(['fr' => '{{app-env-id}}@ssh.{{region}}.frbit.app'])

@task('ls', ['on' => 'fr'])
  ls -lha
@endtask

@task('migrate', ['on' => 'fr'])
  php artisan migrate
@endtask
```

Then execute locally:

```shell
envoy run ls
envoy run migrate
```

## Sending mail

You cannot use [sendmail](/1.platform/03.concepts/09.limits.md) on fortrabbit but Laravel provides an API over the popular SwiftMailer library. The mail configuration file is `app/config/mail.php`, and contains options allowing you to change your SMTP host, port, and credentials, as well as set a global form address for all messages delivered by the library.

## Install Laravel on the server

Alternatively, you can install Laravel directly on the fortrabbit environment instead of developing locally first. Follow these steps:

1. Login to an environment by [SSH](/1.platform/05.code-access/03.ssh.md)
2. Run the above steps to install a Laravel project
3. Move all files in `{project_folder_name}` one level up again

We believe it's better to start with a local development environment first. A local first approach is easier for Git deployments too.
