## About logs

Every environment collects logs from the PHP runtime, the web server and background jobs. The dashboard shows them under the **Logs** tab of the environment.

:BlockLink{title="See logs for {{app-name}} / {{app-env-name}}" path="/environments/{{app-env-id}}/logs"}

## Log sources

The dashboard groups logs into four sources. They follow the path of a request:

```
browser  →  Apache (web server)  →  PHP runtime (app)
            ───────────────────     ─────────────────
            access + error logs     PHP log
```

Apache accepts every HTTP request, applies rewrites and access rules, and hands it to PHP. A failed page shows up as a status code in the access log. The reason sits one layer down: in the PHP log for an error in the app, in the Apache error log for a rewrite or permission problem that never reached the app. Background work writes to the jobs log.

Only output written to `stderr` and `stdout` reaches the PHP and jobs logs. See [log files in the CMS or framework](#log-files-in-the-cms-or-framework) if either stays empty.

### PHP logs

The PHP log holds the errors of the PHP runtime: uncaught exceptions, fatal errors, warnings and notices, plus anything the code sends through `error_log()` or a logger such as Monolog. Each line carries a severity, from `NOTICE` and `WARNING` up to `ERROR`. Filter to `ERROR` to see what broke.

```
[04-Jul-2026 08:15:42 UTC] PHP Warning:  Undefined array key "email" in /data/www/src/Newsletter.php on line 42
[04-Jul-2026 08:15:43 UTC] PHP Fatal error:  Uncaught RuntimeException: Database connection refused in /data/www/src/Db.php:31
```

Look here first when a page turns white or returns a [500 error](/3.dev/22.http-status-codes/500.md): the fatal error and its stack trace are the last `ERROR` line before the failed request. Notices and deprecations appear only when the `error_reporting` of the app includes them.

### Access logs

One line per HTTP request, in the Apache combined log format: client IP, timestamp, method and path, status code, response size, referrer and user agent.

```
203.0.113.7 - - [04/Jul/2026:08:15:42 +0000] "GET /pricing HTTP/1.1" 200 5312 "https://example.com/" "Mozilla/5.0 …"
```

Every request Apache serves is recorded, also those rejected before the app ran. Filter by method, status or IP address to find the URLs returning [404](/3.dev/22.http-status-codes/404.md), or to trace a burst of [503](/3.dev/22.http-status-codes/503.md) or [504](/3.dev/22.http-status-codes/504.md) errors back to one client.

### Apache error logs

The error log of the web server: [.htaccess](/3.dev/21.htaccess/01.intro.md) rewrite mistakes, permission errors, denied access and requests Apache could not route. When a URL misbehaves and the PHP log stays quiet, look here.

Each line carries a severity (`notice`, `warn`, `error`, `crit` …) and often an `AHxxxxx` code, such as `AH01630` for a request denied by server configuration. Search or filter for the code.

```
[Sat Jul 04 08:15:42.123456 2026] [authz_core:error] [pid 12345] [client 203.0.113.7:52134] AH01630: client denied by server configuration: /data/www/.env
```

- [Apache error codes](/3.dev/15.learn/apache-errors.md)

### Jobs logs

The `stdout` and `stderr` output of [jobs](/1.platform/30.jobs/01.usage.md): workers and crons. The source appears once the [Jobs component](/1.platform/09.components/07.jobs.md) is booked. Use it to confirm a cron ran on schedule and to read what a job printed before it stopped.

```
[2026-07-04T08:15:42+00:00] worker.INFO: Processing App\Jobs\SendInvoiceEmail {"id":"9f3c"}
[2026-07-04T08:15:43+00:00] worker.ERROR: SMTP connect failed, retrying in 60s
```

## Browsing and filtering

The log view shows the newest lines first:

- **Filter by level** — limit PHP, Apache error, and Jobs logs to a severity such as `ERROR` or `WARNING`.
- **Filter by method and status** — for access logs, narrow down to a request method (`GET`, `POST`, …) or an HTTP status code (`404`, `500`, …).
- **Filter by IP** — filter for an IP address of an access or Apache error line, or look it up on ipinfo.io.
- **Search** — free-text search across the visible lines.
- **Pick a time range** — jump to a preset like today or yesterday, or define a custom day and hour. Times are UTC.
- **Follow live** — keep the latest lines streaming in as new requests come in.
- **Load more** — page further back through the history.

Click a level, method, status code or IP address in a line to filter for it.

## Logs from a metric

Links below each [metric chart](/1.platform/26.metrics/01.intro.md#chart-box-lines-and-scale) open the logs for the time frame of the chart:

| Metric                                         | Log                                   |
| ---------------------------------------------- | ------------------------------------- |
| PHP response time, PHP memory, OOM kills       | PHP log                               |
| PHP requests, traffic, static requests         | Access log                            |
| 404 and 503 errors                             | Access log, filtered by status code   |
| 500 and 504 errors                             | PHP log and access log                |
| Jobs memory, jobs OOM kills                    | Jobs log                              |

A spike in a metric narrows the time frame. The log lines of that hour name the requests behind it. See [metrics, logs and APM](/1.platform/26.metrics/01.intro.md#metrics-logs-and-apm).

## Downloading logs

To keep logs or analyze them elsewhere, switch to **Download** and pick a source and a time range. The file downloads in the browser, or a link arrives by e-mail. Large ranges take a few minutes to prepare.

## Tailing logs over SSH

To follow the logs in the terminal:

1. Log in to the environment by [SSH](/1.platform/05.code-access/03.ssh.md)
2. Run `frbit-tail-logs`

This tails `stderr` and `stdout` as a live stream.

## Log files in the CMS or framework

A CMS or framework that writes logs to its own files, instead of `stderr` and `stdout`, does not show up in the dashboard. Read those files over [SSH](/1.platform/05.code-access/03.ssh.md) or [SFTP](/1.platform/05.code-access/04.sftp.md); the CMS or framework docs name the location.

Most CMS and frameworks can send logs to `stderr`. The [software template](/1.platform/03.concepts/05.software-templates.md) sets this by ENV var where possible.

- [Craft CMS logging](/2.guides/3.craft-cms/06.tune.md#logging)
- [Laravel logging](/2.guides/2.laravel/05.tune.md#logging)

### Verbose logging

Verbose or debug logging prints more detail with each error and sometimes shows errors in the browser. It slows the app down and can expose internals, so keep it to development and staging. When a production issue needs it, turn it off again afterwards.
