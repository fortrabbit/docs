## Use cases

- Building an integration, a bot, or a custom dashboard
- A capability is missing from the [CLI](/1.platform/04.automation/03.cli/01.intro.md) and the [MCP server](/1.platform/04.automation/02.mcp.md)
- A script, CI job or server needs a credential, and no browser is at hand

## API reference docs

The full endpoint reference is generated from the API itself and lives at:

- [api.fortrabbit.com/v1/docs](https://api.fortrabbit.com/v1/docs)
- OpenAPI description, for code generators and agents: [api.fortrabbit.com/v1/docs.jsonopenapi](https://api.fortrabbit.com/v1/docs.jsonopenapi)

## Entry point

All endpoints sit under a single base URL:

```
https://api.fortrabbit.com/v1
```

Send `Accept: application/json` on every request. Without it the API answers in JSON-LD, which carries extra `@`-prefixed metadata most clients do not expect.

## Authentication

The API authenticates with a personal API token. A token acts as the person who created it, limited to the [apps](#token-apps) chosen for it. Tokens are managed in the dashboard, under [API tokens](https://dash.fortrabbit.com/credentials/api-tokens). The [CLI](/1.platform/04.automation/03.cli/01.intro.md) authenticates with an OAuth token instead, issued by `frbit auth login`. Both go in the same header. Pass the token as a bearer token on every request:

```shell
curl https://api.fortrabbit.com/v1/apps \
  -H "Authorization: Bearer frbit-at-YOUR-TOKEN" \
  -H "Accept: application/json"
```

### Create a token

The token is created in the dashboard in four steps:

1. A name to recognize it later, and when it [expires](#token-expiry)
2. The [apps](#token-apps) it reaches
3. The [permissions](#token-permissions) it gets
4. The token itself, to copy

:BlockLink{title="Create a new API token" path="/new/api-token"}

The full token is shown once, on the final step of that flow, and cannot be retrieved later. Copy it before leaving the page. A lost token cannot be recovered — delete it and create a new one.

### Token permissions

Permissions limit which HTTP methods a token may send. Choose the smallest set that covers the job:

| Permission             | Allowed methods                         |
| ---------------------- | --------------------------------------- |
| Read                   | `GET`                                   |
| Read and write         | `GET`, `POST`, `PUT`, `PATCH`           |
| Read, write and delete | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |

`Read` is preselected. Permissions cannot be changed later — create a new token and delete the old one instead. A request with a method the token does not cover answers `403`, with a message naming the method. Restoring a backup is a `POST`, but it overwrites data, so it needs `Read, write and delete`. The same goes for switching a component off.

Tokens created before permissions were introduced kept full access.

### Token apps

A token reaches `All apps` or `Chosen apps`. `All apps` is preselected and covers every app the person has developer access to, also apps added later. `Chosen apps` covers the checked apps, plus the apps the token creates itself. An app created in the dashboard or by a colleague stays out: create a new token for it.

An app outside the list answers `404`, like an unknown ID, and so do its environments, deployments and domains. Lists leave them out. When the person loses developer access to an app, or the app is deleted, the token loses it too.

Teams and payment methods have no app, so only the permissions apply to them. Deleting a team or a payment method that would also delete an app outside the list answers `403` and deletes nothing.

`GET /v1/apps` lists only apps with developer access, for every token. An app the person only pays for answers `404`.

### Token expiry

`Expires after` offers `1 day`, `7 days`, `30 days`, `90 days`, `1 year` and `No expiry`. `90 days` is preselected. An expired token answers `401` with a message naming the token, such as `API token "Deploy" expired on 2027-02-17. Create a new token.` Expired tokens are deleted 30 days after they expire. Tokens created before expiry was introduced do not expire.

### frbit CLI tokens

A token from `frbit auth login` can read and write. It reaches the apps chosen on the approval page, like an [API token](#token-apps). It can delete only when `Allow deletes` was ticked when approving the connection. That covers every `DELETE`, restoring a backup and switching a component off. Without it, these requests answer `403` and ask to run `frbit auth login` again. The connection ends one year after approval, or after 30 days without use, whichever comes first. See [CLI authentication](/1.platform/04.automation/03.cli/03.setup.md#sign-in).

### List and delete tokens

Tokens for the account are listed in the dashboard. A click on a token opens its permissions, apps, expiry, the date of the last use and the user agent of that request. Clients send any user agent they like, so it is a hint.

:BlockLink{title="Your API tokens" path="/credentials/api-tokens"}

Apps, permissions and expiry cannot be changed later. Create a new token, switch the client over, wait until the old token shows no new use, then delete it: `Delete` on the token page, then confirm. Deleting takes effect immediately, every other token of the account keeps working.

## API coverage

| Resource          | Path                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------- |
| Own account       | `/v1/you`                                                                                            |
| SSH keys          | `/v1/ssh-keys`                                                                                       |
| Apps              | `/v1/apps`, `/v1/apps/{id}/git-repository`                                                           |
| Environments      | `/v1/environments`, `/v1/environments/{id}/restart`                                                  |
| Components        | `/v1/environments/{id}/components`                                                                   |
| Variables         | `/v1/environments/{id}/environment-variables`                                                        |
| Settings          | `/v1/environments/{id}/php-settings`, `/v1/environments/{id}/mysql`, `/v1/environments/{id}/basic-auth` |
| Firewall rules    | `/v1/environments/{id}/firewall-rules`, `/v1/firewall-rules`                                         |
| Jobs              | `/v1/environments/{id}/jobs`, `/v1/jobs`, `/v1/jobs/check-cron`                                      |
| Backups           | `/v1/environments/{id}/backups`, `/v1/backups/{id}/restore`, `/v1/backups/{id}/download/{type}`      |
| Deployments       | `/v1/deployments`, `/v1/deployments/{id}/logs`, `/v1/environments/{id}/deployments`                  |
| Logs and metrics  | `/v1/environments/{id}/logs`, `/v1/environments/{id}/metrics`, `/v1/environments/{id}/metrics/{metric}` |
| Domains           | `/v1/domains`, `/v1/domains/{id}/dns`, `/v1/environments/{id}/main-domain`                           |
| Teams             | `/v1/teams`                                                                                          |
| People            | `/v1/people`                                                                                         |
| Payment methods   | `/v1/payment-methods`                                                                                |
| Catalog, no token | `/v1/catalog/*`                                                                                      |

Adding and deleting SSH keys works only with a `frbit auth login` that is not limited to apps. An API token answers `403`.

Objects are addressed by their public ID — the same short `ap-`, `en-`, `do-` identifiers the dashboard shows. Collections accept a repeated `publicId[]` parameter to fetch several known objects in one call.

## Requests and responses

### Pagination

Lists of apps, environments, domains, deployments, teams and payment methods come in pages of 30, selected with `?page=`. Every page carries two headers:

- `X-Total-Count`: the number of items in the whole list
- `Link`: the URLs of the first, previous, next and last page

### Unknown fields

A write with a field the endpoint does not know answers `422` and names the field. A typo in a field name fails instead of being ignored.

### Retries

Every `POST` accepts an `Idempotency-Key` header with a unique value of up to 255 characters. A retry with the same key and the same request returns the first response again, marked with `Idempotent-Replayed: true`, and does not run twice:

```shell
curl -X POST https://api.fortrabbit.com/v1/environments/en-abc123/restart \
  -H "Authorization: Bearer frbit-at-YOUR-TOKEN" \
  -H "Accept: application/json" \
  -H "Idempotency-Key: 7f3c9a1e-restart-1"
```

- The same key with a different request answers `422`.
- The same key while the first request still runs answers `409`.
- Responses are kept for 24 hours.
- Keys are scoped per token: another token with the same key runs the request.

### Errors

Errors answer with `Content-Type: application/problem+json`:

```json
{
  "type": "about:blank",
  "title": "Forbidden",
  "status": 403,
  "detail": "This API token has no scope permitting DELETE requests.",
  "error": "This API token has no scope permitting DELETE requests."
}
```

- The fields follow RFC 9457. `type` is always `about:blank`, `title` is the HTTP status phrase, `detail` says what went wrong.
- `error` repeats `detail`, for older clients and scripts.

| Status | Meaning                                                                                                              |
| ------ | -------------------------------------------------------------------------------------------------------------------- |
| `400`  | The body is not valid JSON.                                                                                          |
| `403`  | The resource is visible to you, but the token permissions or your team role do not allow the request.                |
| `404`  | The ID is unknown, or outside your access or the token's apps. All answer the same, so IDs of others stay hidden.   |
| `422`  | The input is invalid. `violations` lists each `propertyPath` with its `message`, `errors` keeps the older field map. |
| `429`  | The [rate limit](#rate-limits) is used up.                                                                           |

### Prices before creating

`POST /v1/apps` and `POST /v1/environments` return the monthly price of the new environment, in cents, with the currency. With `"dryRun": true` in the body they run every check and return only the price, without creating anything.

## Catalog

The catalog lists what the create endpoints choose from: regions, component plans with prices, software presets, PHP and Node.js versions, PHP extensions and PHP settings. It lives under `/v1/catalog/` and needs no token:

```shell
curl https://api.fortrabbit.com/v1/catalog/component-plans?currency=USD \
  -H "Accept: application/json"
```

Catalog responses may be cached for an hour.

## Rate limits

Requests are counted per token in a sliding window of one minute. A frbit CLI connection counts as one token: its tokens renew while it runs, and they share one budget. Every response carries the limit in `X-RateLimit-Limit`, with `X-RateLimit-Remaining` and `X-RateLimit-Reset`; a rejected request answers `429` and adds `Retry-After` with the seconds to wait. The catalog without a token has its own limit, per IP address. Failed authentications are counted separately, per IP address. Retrying a rejected credential in a loop locks the address out rather than the token.

## Stability

The API is in [BETA](/1.platform/01.new/3.beta.md) like the whole platform. Breaking changes are possible while that lasts, though not planned. The `/v1` prefix marks the version of the API.
