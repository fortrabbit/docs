## Get ready

- You need to have setup [SSH keys](/3.dev/15.learn/01.ssh-key-setup.md) to authenticate.
- See the direct [code access intro](/1.platform/05.code-access/01.intro.md) for use cases and limits.

## Accessing SSH

Each [environment](/1.platform/10.objects/02.environment.md) has its own SSH access. Execute the following in your terminal to login:

:BlockLink{title="See SSH access for {{app-name}} / {{app-env-name}}" path="/environments/{{app-env-id}}/ssh"}

```shell
# Connect to your environment via SSH
$ ssh {{app-env-id}}@ssh.{{region}}.frbit.app
```

If the login went well, you will see a small welcome message:

## Executing scripts

Scripts with the executable bit and a shebang line run directly. A PHP file without the executable bit runs through the PHP interpreter:

```shell
$ php artisan some:command
$ php some-script.php
$ vendor/bin/drush status
```

Some Composer binaries, `vendor/bin/drush` among them, are shell scripts. Call them directly: `php vendor/bin/drush` prints the script instead of running it.

## Using Composer

With [Git deployment](/1.platform/06.deployment/01.intro.md), the build commands run [Composer](/3.dev/15.learn/02.composer.md), so there is no need to run it over SSH. When it is needed, run `composer install`, never `composer update`: an update changes the versions on the environment and leaves the local `composer.lock` behind.

## Limitations

- No root shell: software packages cannot be installed or removed, see [limits](/1.platform/03.concepts/09.limits.md).
- The SSH session shares memory and CPU with the web requests. A heavy command slows the website down; run it as a [job](/1.platform/30.jobs/01.usage.md) instead.
- Jobs are managed in the dashboard, not in the shell.
