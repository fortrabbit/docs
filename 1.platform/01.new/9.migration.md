## Timeline

Migration runs in batches. It starts once the new platform leaves beta with feature parity. A first pilot wave is planned for autumn 2026: newer Universal Apps, mostly in the US region. Newer apps go first because their setup is closest to what the new platform expects. Later waves take on older apps, larger setups, and apps that need code or config work. The program is planned to complete in 2027.

## Communication

Affected customers receive an e-mail with the plan and a time frame ahead of each batch. Batches are opt-out: owner can ask to postpone to the next wave. We will also notify affected customers, once apps have been migrated.

## Account migration

Matching accounts are created on the new platform. Identity and billing carry over. The structure maps like this:

- companies → teams
- billing contacts → payment methods
- apps have environments now (at least one)

Login is planned to work on both platforms, a new password may be required.

## App migration

Apps follow once accounts are in place. Steps per app:

1. Apps, environments and domains pre-created and pre-configured.
2. Code, files and database copied over.
3. Review by fortrabbit staff.
4. DNS switch (see below).
5. Old app deleted a few days later.

### DNS switch

fortrabbit performs the DNS switch, traffic moves without downtime and without interaction. A hop points the old CNAME-based app URL at the new test domain:

```raw
domain → {{appname}}.frb.io → {{env-id}}.{{region}}.frbit.app
```

Recommended: Pointing the domain straight at the new test domain afterwards removes the extra hop.

## After the migration

What changes once an app runs on the new platform:

- New dashboard at [dash.fortrabbit.com](https://dash.fortrabbit.com).
- The fortrabbit-hosted Git repository is gone. Deploy through the GitHub integration, or over SSH/SFTP/rsync.
- SSH/SFTP login with username and password is gone, SSH keys are required.
- The SSH/SFTP host URLs changed. Pick up the new ones from the new dashboard.
- See [playtform changes](changes) for all details.

### Suggested next steps

- Review the app. We test migrated apps, but cannot know each code base and its requirements.
- Download a fresh code backup from the new platform.
- Move deployment to the [GitHub integration](/1.platform/06.deployment/02.github-app.md), the only Git host supported for now.

## Billing

Migration is free. The price level stays about the same, individual bills may vary. Billing is in arrears per app on daily usage, so overlap stays minimal.

### Pricing adjustments

App plans map to the new components as closely as possible. Many apps end up cheaper, some configurations cost more.

### Full migration case

When all apps of a customer move at once, the migration month brings one invoice from each platform. After that, only the new platform is billed.

### Partial migration case

Some apps may stay behind, because the owner opted out or the app needs further adjustments. Invoices then come from both platforms until the migration completes, billed per app. Nothing is charged twice.

## Code/config adjustments

Apps kept up to date and configured with ENV variables need no changes. Where that is not the case, we may adjust code or config: a `composer update`, a framework version bump, or hardcoded config values.

## Drift

The window between backup, install and DNS switch is short, so drift stays small. Changes to account settings, app settings or content made inside that window can still get lost. Avoid them until the switch is done.

## Self-service migration

Early adopters do not have to wait. The [self-service migration guide](/1.platform/01.new/8.self-migration.md) walks through moving an app by hand: deploy the code base, import the database, copy the media library into persistent storage.

Please :ContactUs{text="contact us"} at any point. We provide hands-on assistance and can offer a discount during the migration period.
