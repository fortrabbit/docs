Git holds the versions of the code and also carries the changes to fortrabbit.

## High-level concept

```raw
1 Local   2 Git provider   3 fortrabbit       4 environment
┌─────┐   ┌────────────┐   ┌──────────────┐   ┌──────────────┐
│ Git ├───▶  Git repo  ├───▶  Deployment  ├───▶   storage    │
└─────┘   └────────────┘   └──────────────┘   └──────────────┘
```

1. Work in the local Git repo.
2. Push to GitHub. The push triggers a deployment, see [deployment trigger](/1.platform/06.deployment/05.trigger.md).
3. The deployment service of fortrabbit builds the code.
4. The result goes into the storage of the [environment](/1.platform/10.objects/02.environment.md).

## Deployment steps

A [deployment](/1.platform/10.objects/11.deployment.md) passes these steps, shown in the dashboard:

1. **Pending**: waiting for a free slot.
2. **Preparing**: the deployment container starts and pulls the code from the Git repo.
3. **Building**: the [build commands](/1.platform/06.deployment/03.build-commands.md) run, such as `composer install` and `npm run build`.
4. **Distributing**: the result goes into the storage, according to the [deployment strategy](/1.platform/06.deployment/08.strategy.md), then the [post deploy commands](/1.platform/06.deployment/04.post-deploy-commands.md) run.
5. **Succeeded** or **failed**: the [deploy log](/1.platform/06.deployment/17.logs.md) shows the output of every step.

After each successful deployment, all [jobs](/1.platform/30.jobs/01.usage.md), workers and crons, restart and run the new code.

## Code moves up, content moves down

Development happens in the [local development environment](/4.integrations/01.local-development/01.intro.md), and code changes are pushed up. Content often comes from the other side: an editor adds a blog post in production.

| What                          | Git deployment | Alternative |
| ----------------------------- | -------------: | ----------: |
| Code and dependencies         |            Yes |           - |
| Database contents             |             No |        dump |
| Image uploads and other files |             No |       rsync |

[Code access](/1.platform/05.code-access/01.intro.md) by [SSH](/1.platform/05.code-access/03.ssh.md) and [SFTP](/1.platform/05.code-access/04.sftp.md) moves content in both directions.

## What the storage contains

The storage is not a copy of the Git repo. It holds:

1. The code from the latest deployment
2. Build results, such as the `vendor` folder and compiled assets
3. Changes made by code access
4. Runtime data like uploads, logs and cache files

The [deployment strategy](/1.platform/06.deployment/08.strategy.md) decides what happens to files that are not in the deployment: replace deletes them, merge keeps them. [Exclude patterns](/1.platform/06.deployment/10.exclude-patterns.md) protect runtime data with both.

## Git only syncs up

Git deployment goes one way, from the repo to the environment. A file uploaded by SFTP cannot be pulled into the Git repo with `git pull`. This keeps uploads, binaries and other runtime data out of the repo: Git holds the code, SSH and SFTP handle the content.

## Software and Git

Git deployment works best with software that keeps code and content in separate folders and installs its dependencies with [Composer](/3.dev/15.learn/02.composer.md). [Laravel](/2.guides/2.laravel/01.install.md), [Symfony](/2.guides/7.more/08.symfony.md) and [Craft CMS](/2.guides/3.craft-cms/01.install.md) work this way. [WordPress](/2.guides/6.wordpress/01.setup.md) and other CMS mix code and content in one folder and need exclude patterns to deploy by Git.
