## When you need one

Usually not. fortrabbit deploys every push to GitHub with its own [build and deployment](/1.platform/06.deployment/01.intro.md) service, see [build commands](/1.platform/06.deployment/03.build-commands.md). A CI pipeline makes sense when tests have to pass before a deployment, or when the build needs tools the build commands do not have, see [GitHub Actions](/4.integrations/03.git-providers/02.github.md).

## Runner types

| Type | Where jobs run | Providers |
| -- | -- | -- |
| Managed | The provider's cloud, switched on with a `runs-on` label | [Namespace](/4.integrations/12.github-actions-runners/02.namespace.md), [Blacksmith](/4.integrations/12.github-actions-runners/06.blacksmith.md), [Ubicloud](/4.integrations/12.github-actions-runners/07.ubicloud.md), [Depot](/4.integrations/12.github-actions-runners/10.depot.md) |
| Managed or own cloud | The provider's cloud or your AWS, GCP or Azure account | [WarpBuild](/4.integrations/12.github-actions-runners/05.warpbuild.md) |
| Own cloud | VMs in your cloud account, started per job | [RunsOn](/4.integrations/12.github-actions-runners/08.runs-on.md), [Cirun](/4.integrations/12.github-actions-runners/09.cirun.md) |
| Own servers | Servers you run | [Actuated](/4.integrations/12.github-actions-runners/04.actuated.md), GitHub's [self-hosted runner](https://docs.github.com/en/actions/hosting-your-own-runners) |

Managed runners trade control for less work. Runners in your own cloud keep code and data in your account, and you pay the cloud bill.

## Deploy to fortrabbit

fortrabbit needs no integration with the runner. The final workflow step uploads the build over SSH, for example with [rsync](/3.dev/20.how-to/rsync.md), authenticated with a [deploy key](/1.platform/10.objects/12.ssh-key.md#deploy-keys).

More self-hosted runner tools are listed in [jonico/awesome-runners](https://github.com/jonico/awesome-runners) on GitHub.
