## About image transforms

Most CMS and many apps create resized copies of uploaded images: thumbnails, responsive sizes, WebP or AVIF versions. Each copy is a transform. PHP loads the full source image into memory and resizes it with GD or ImageMagick. A 6000 pixel camera photo takes about nine times the memory of a 2000 pixel one, and one upload can trigger many transforms at once, one per size and format. With files on S3 or another remote storage, PHP also downloads the source and uploads every result.

When that runs in the PHP processes that serve the site, requests run into the timeout and return a [504 error](/3.dev/22.http-status-codes/504.md), or a process runs [out of memory](/3.dev/02.performance/10.out-of-memory.md). Other visitors wait for a free [PHP process](/3.dev/02.performance/06.php-processes.md) meanwhile.

## Crunch images in a worker

We recommend a [worker job](/1.platform/30.jobs/03.workers.md) for image transforms. The worker runs the queue of the app in its own container: it resizes images in the background while the PHP processes keep serving visitors. Image optimizers such as `jpegoptim` or `pngquant` are installed in [jobs](/1.platform/09.components/07.jobs.md) only, so they run there too.

1. Book the [jobs component](/1.platform/09.components/07.jobs.md).
2. Set up the queue of the app, so transforms become queue jobs instead of running in the request.
3. Add a worker job with the queue command of the software.
4. Turn off queue processing in web requests, where the software has it.

| Software | Worker command | Path |
| -- | -- | -- |
| Craft CMS | `php craft queue/listen --verbose` | [Craft CMS image transforms](/2.guides/3.craft-cms/16.image-transforms.md) |
| Laravel | `php artisan queue:work` | [Laravel image conversions](/2.guides/2.laravel/07.queues-scheduler.md#image-conversions) |
| Statamic | `php artisan queue:work` | [Statamic image presets](/2.guides/5.statamic/04.tuning.md#image-presets) |
| Kirby | Plugin, untested | [Kirby thumbs](/2.guides/4.kirby/10.tune.md#thumbs) |
| WordPress | Plugin, untested | [WordPress image sizes](/2.guides/6.wordpress/02.tune.md#image-sizes) |

## When transforms run

Without a worker, transforms run in a web request:

| Trigger | Runs in |
| -- | -- |
| Upload | The upload request |
| First view of the image URL | That image request |
| Page render | The page request |
| Queue processed by web requests | A page request |

Transforms triggered by a URL can also be triggered by bots, and they fill the [storage](/1.platform/09.components/03.storage.md#why-storage-grows).

## Keep source images small

A worker still needs memory for every image.

- Scale images down before uploading them. Twice the largest display size is enough for high-density screens.
- Define fewer sizes and formats. Every combination is another file to generate and store. [Page weight](/3.dev/02.performance/09.page-weight.md) covers the ones worth generating.
