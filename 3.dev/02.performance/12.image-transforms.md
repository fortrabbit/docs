## About image transforms

Most CMS and many apps create resized copies of uploaded images: thumbnails, responsive sizes, WebP or AVIF versions. Each copy is a transform. PHP loads the full source image into memory and resizes it with GD or ImageMagick, both installed on every environment.

Memory grows with the pixel count. A 6000 pixel camera photo takes about nine times the memory of a 2000 pixel one. One upload can trigger many transforms at once, one per size and format. With files on S3 or another remote storage, PHP also downloads the source and uploads every result.

When that runs in the PHP processes that serve the site, requests run into the timeout and return a [504 error](/3.dev/22.http-status-codes/504.md), or a process runs [out of memory](/3.dev/02.performance/10.out-of-memory.md). Other visitors wait for a free [PHP process](/3.dev/02.performance/06.php-processes.md) meanwhile.

## When transforms run

| Trigger | Runs in |
| -- | -- |
| Upload | The upload request |
| First view of the image URL | That image request |
| Page render | The page request |
| Queue job | Web request or worker, depending on the queue |

Transforms triggered by a URL can also be triggered by bots, and they fill the [storage](/1.platform/09.components/03.storage.md#why-storage-grows).

## Move transforms to a worker

Run the queue of the app in a [worker job](/1.platform/30.jobs/03.workers.md). The worker generates transforms in its own container, outside the PHP processes that serve the site. Image optimizers such as `jpegoptim` or `pngquant` are installed in [jobs](/1.platform/09.components/07.jobs.md) only.

## Keep source images small

- Scale images down before uploading them. Twice the largest display size is enough for high-density screens.
- Define fewer sizes and formats. Every combination is another file to generate and store. [Page weight](/3.dev/02.performance/09.page-weight.md) covers the ones worth generating.
