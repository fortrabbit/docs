## PHP processes

fortrabbit runs PHP with PHP-FPM, the FastCGI Process Manager. Its processes stay alive between requests. Each one handles one PHP request at a time. The [PHP plan](/1.platform/09.components/01.php.md) sets the number of processes and the memory they share.

## PHP memory requirements

How much memory your website will require depends on multiple factors. Let's start with the theory:

- Extensions: Each enabled PHP extension must be loaded into memory.
- PHP libraries: You most likely are using Composer to manage your dependencies. This implies a set of PHP files which need to be interpreted and loaded into memory - specifically into the OPcache.
- PHP code: The code you write yourself consumes memory in the OPcache as well. The more code you have, i.e. the more functions and complexity, the more memory is required.
- Runtime variables: In each request your App fills variables (`$foo = "bar"`), which consumes memory. How much it will use depends on the amount of data used in variables. Measure it with [memory_get_peak_usage()](https://www.php.net/manual/en/function.memory-get-peak-usage.php).

The memory used by extensions and OPcache is shared. This means: If you run an app on a single process and use 10 MB OPcache, then you will also only use 10 MB of OPcache with two processes. The memory consumed by runtime variables is not shared. It's hard to pre-calculate the expected memory usage.

The tricky part is the data size. Say you have a blog with comments using a database. Now rendering a small blog entry with no comments will utilize less memory than rendering a large blog entry with thousands of comments. That depends on the code. It could load all of the thousands of comments into a PHP array and then render the site or load them in batches and print them right away, with very different memory use. Expect memory use to grow with the data. See [out of memory](/3.dev/02.performance/10.out-of-memory.md).

## PHP processes, PHP requests, PHP response time

- A PHP request should finish quickly. The [metrics](/1.platform/07.settings/30.metrics.md) mark a PHP response time below 150 ms as fast, below 350 ms as good and 700 ms as slow.
- A new request waits when all PHP processes are busy.
- The PHP response time is most of the time to first byte (TTFB); network latency adds the rest.

### A simple example

- The environment has 2 PHP processes
- 1 PHP request takes 500 ms (PHP response time)
- Each process handles 2 requests per second, so the environment handles 4 per second

### A bad example

- The environment has 4 PHP processes
- 1 PHP request takes 1,000 ms
- 1 page view creates 3 PHP requests
- 3 visitors at the same moment create 9 requests: 4 run, 5 wait. With a steady stream of visitors the queue grows until requests time out

## PHP processes VS page views

Page views refer to a single request made by a user to view a page on a website. This request will likely involve a number of HTTP requests, such as images, HTML, CSS, and JavaScript files, all of which must be downloaded from the web server.

For many websites, one page view is one PHP request. Often it is more: AJAX calls, API requests or image transforms each take a PHP process.

## PHP processes VS max execution time

A higher `max_execution_time` lets long tasks finish, and lets them block a PHP process for longer, see the examples above. Keep it low in the [PHP settings](/1.platform/07.settings/06.php.md) and move long tasks to [jobs](/1.platform/09.components/07.jobs.md). A request to an external API that has not answered in 10 seconds rarely answers at all.
