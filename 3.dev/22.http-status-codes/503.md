## What the logs show

A PHP process that dies mid-request writes no PHP error. Look in the Apache error log in the [logs](/1.platform/07.settings/25.logs.md) instead:

| Code | Meaning |
| -- | -- |
| [`AH01067`](/3.dev/15.learn/apache-errors.md#ah01067-failed-to-read-fastcgi-header) `Failed to read FastCGI header` | PHP returned no response header: the worker crashed, timed out or was killed |
| [`AH01075`](/3.dev/15.learn/apache-errors.md#ah01075-error-dispatching-request) `Error dispatching request` | The connection to PHP broke off mid-request |

Both point to a PHP process that never finished, not to a problem with Apache.

## Common causes

| Cause | Sign | Next step |
| -- | -- | -- |
| Out of memory | OOM kills in the PHP [metrics](/1.platform/26.metrics/05.php.md#oom-kills) | [Out of memory](/3.dev/02.performance/10.out-of-memory.md) |
| All PHP processes busy | High PHP response time, often also 504 errors | [504 errors](/3.dev/22.http-status-codes/504.md), [PHP processes](/3.dev/02.performance/06.php-processes.md) |
| A crash in code or an extension | 503 on one page or action only | Turn off plugins or recent code until it stops |

A 503 also appears without any deployment: more traffic, a bot, a bigger database or an editor's action can push the app past its limits. See [performance problems are often people problems](/3.dev/02.performance/02.people-problems.md).

## Restart as a workaround

The restart button of the [environment](/1.platform/10.objects/02.environment.md#restarting-an-environment) restarts Apache and PHP. That frees stuck processes, with a short downtime. The 503 returns when the cause stays.

## Platform status

When none of the above fits, check the [fortrabbit status page](https://fortrabbit.betteruptime.com/) for incidents.
